## 1. Contexte

Audit complet du systeme de notifications declenche par deux constats :

1. **Bug reporte par les utilisateurs** : une notification fermee/lue sur
   telephone restait affichee non-lue sur PC (et inversement).
2. **Manques fonctionnels** : le MJ n'etait prevenu de rien sur sa propre table
   (inscriptions, departs, liste d'attente), et les changements d'evenement
   n'alertaient personne.

L'audit a produit une spec (6 bugs avec cause racine + inventaire des
notifications manquantes) et une roadmap en 6 lots. Les lots A a E sont faits,
le lot F (optionnel) reste a discuter.

## 2. Lot A — Sync multi-appareils + fixes UX (bug utilisateurs)

### Cause racine du bug reporte

Le backend n'emettait **aucun** evenement socket lors du mark-as-read /
read-all / delete — seul `notification:new` existait. Chaque appareil (et
chaque onglet) gardait son etat local jusqu'a un rechargement de page.
Structurel, pas aleatoire.

### Corrections livrees

| Fix                        | Detail                                                                                                                                                                                                                                                                                                                |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sync multi-appareils       | `services/notification.ts` emet `notification:read { id }`, `notification:read-all {}`, `notification:deleted { id }` vers la room `user:<userId>` ; `useNotifications` les applique avec des mutations idempotentes (l'echo de sa propre action ne double-decremente jamais le compteur, item hors page charge gere) |
| Panneau qui restait ouvert | Clic sur une notification = fermeture du dropdown (desktop) / de la MobileSheet (mobile) avant navigation                                                                                                                                                                                                             |
| Impasse 403                | "Retire d'un evenement" naviguait vers une page interdite ; table de routage par type : `PARTICIPANT_REMOVED`/`EVENT_DELETED` -> `/events`, `TABLE_DELETED`/`PLAYER_KICKED` -> planning sans deep-link `?table` (la cible n'existe plus)                                                                              |
| Doublons                   | Dedoublonnage par id du handler `notification:new` (course refetch/socket a la reconnexion)                                                                                                                                                                                                                           |
| 500 injustifies            | `createNotification`/`createBulkNotifications` non-bloquants : un echec d'insert est logge et ne fait plus echouer l'action metier (kick, promotion...) deja commitee                                                                                                                                                 |

### Verification specifique

Script de verification execute sur le stack Docker reel : deux clients socket
connectes avec la meme session ont bien recu `read`, `read-all` et `deleted`
apres les appels API correspondants.

## 3. Lot B — Notifications MJ (le manque principal)

Migration Prisma **additive** (`ALTER TYPE "NotificationType" ADD VALUE`) :
4 nouveaux types. Schema du discord-bot resynchronise au passage (il avait
deja derive : `RESERVED_SEAT_ASSIGNED` manquait).

| Type                   | Declencheur                           | Message (exemple)                                 |
| ---------------------- | ------------------------------------- | ------------------------------------------------- |
| `GM_PLAYER_JOINED`     | Un joueur rejoint (place confirmee)   | "<joueur> a rejoint ta table \"<titre>\""         |
| `GM_PLAYER_WAITLISTED` | Un joueur arrive en liste d'attente   | "<joueur> est en liste d'attente sur \"<titre>\"" |
| `GM_PLAYER_LEFT`       | Un joueur quitte la table             | "<joueur> a quitté \"<titre>\""                   |
| `GM_TABLE_FULL`        | Le join qui remplit la derniere place | "Ta table \"<titre>\" est complète"               |

Regles anti-bruit : jamais de notification au MJ pour ses propres actions ;
l'auto-assise du MJ a la creation d'une table JDS ne genere rien.

**Angle mort admin corrige** (decouvert a l'audit) : les routes table sont en
`requireTableGMOrAdmin` — un admin pouvait modifier ou supprimer la table d'un
MJ sans que celui-ci le sache, car le MJ de JDR (non joueur) n'est pas dans les
participants. `updateTable` et `deleteTable` incluent maintenant le createur
dans les destinataires quand l'auteur est quelqu'un d'autre (types existants
`TABLE_UPDATED`/`TABLE_DELETED`, aucune migration).

Icones front : 🙋 rejoint, ⏳ liste d'attente, 👋 depart, 🎉 table complete.

## 4. Lot C — Notifications event (types morts cables)

`EVENT_UPDATED` et `EVENT_DELETED` existaient dans l'enum et le front depuis le
debut mais n'etaient **jamais crees** : un admin pouvait supprimer un event
sans que personne ne soit prevenu.

- `EVENT_UPDATED` : emis aux participants (sauf auteur) uniquement si un champ
  **significatif** change (nom, dates). Un changement technique (discordRoleId)
  ne notifie personne.
- `EVENT_DELETED` : participants recuperes avant le delete cascade, notifies
  apres (sauf auteur). Le clic mene a `/events` (l'event n'existe plus).
- Emissions socket ajoutees : `event:updated` / `event:deleted` vers la room
  de l'event (les pages ouvertes pourront s'en servir plus tard).
- La purge (`purgeEvent`) reste volontairement silencieuse (inchangee).
- Signatures `updateEvent`/`deleteEvent` : parametre auteur ajoute pour
  l'exclusion (controllers passent `req.session.userId`).

## 5. Lot D — Retention

La table `Notification` grossissait indefiniment. Job quotidien lance au boot
du serveur (`server.ts`, absent des tests) :

- notifications **lues** de plus de **30 jours** : supprimees ;
- notifications **non lues** de plus de **90 jours** : supprimees ;
- best-effort (echec logge, jamais bloquant), `timer.unref()` pour ne pas
  empecher l'arret du process.

---

## 6. Lot E — Tests E2E (aucun n'existait sur les notifications)

Nouveau spec `e2e/notifications.spec.ts` (Playwright, Chromium, vrai
navigateur sur le stack Docker) :

1. **Temps reel MJ** : un joueur rejoint via l'API -> le badge du MJ passe a 1
   sans reload -> le panneau montre "Nouveau joueur" -> le clic navigue vers
   `/events/:id/planning?table=<id>`, ouvre la modale de la table, ferme le
   panneau et marque la notification lue (badge vide).
2. **Sync multi-onglets** : deux onglets de la meme session voient le badge
   apparaitre en live ; "Tout marquer lu" sur l'onglet A vide le badge de
   l'onglet B sans action ni reload — le scenario exact du bug reporte.
